# UNIDOAR — guía del proyecto

Marketplace que conecta **instituciones** (colegios, clubes, natatorios) con **docentes, entrenadores y guardavidas** verificados. Este repo es la app real (Next.js); el prototipo navegable original vive en `prototipo/` y es **solo referencia visual y de copy**. `HANDOFF.md` documenta pantallas y tokens de marca.

## Stack

- Next.js 16 (App Router, `src/`), React 19, TypeScript estricto, Tailwind 4, pnpm.
- **Supabase** (Vercel Marketplace) para todo lo de backend: **Postgres** accedido con **Drizzle ORM** + `postgres-js` (`src/db`), **Auth** (`@supabase/ssr`, sesión en cookies) y **Storage** (buckets `publico` y `privado`).
- Deploy: Vercel, proyecto `unidoar-prototipo` (equipo Cambalaches), funciones en `gru1` (junto a la base). `main` es producción y es donde se trabaja: se despliega solo en cada push. El prototipo estático quedó en `prototipo/` como referencia.
- **Dominio:** `https://www.unidoar.com.ar` (el DNS está en Vercel; `unidoar.com.ar` sin `www` redirige). Usar y compartir **solo ese**: la sesión y el enlace de confirmación del registro dependen del host, y `NEXT_PUBLIC_SITE_URL` (Vercel) apunta a él; también responde `unidoar-prototipo.vercel.app`, que sirve para `/api/salud` pero no para registrarse. En el código no hay ninguna dirección fija: todo sale de esa variable o del host del pedido.
- En Next 16 el antiguo `middleware` se llama **`proxy.ts`** (`src/proxy.ts`). Antes de usar una API de Next, leé la guía correspondiente en `node_modules/next/dist/docs/`.

## Comandos

```bash
pnpm dev            # servidor local
pnpm typecheck      # tsc --noEmit  (correrlo siempre antes de dar algo por hecho)
pnpm lint
pnpm test           # pruebas de la lógica pura (src/**/*.test.ts, node:test vía tsx): sin base, sin red, en menos de un segundo
pnpm db:push        # aplica src/db/schema.ts a la base (desarrollo)
pnpm db:rls         # activa RLS en todas las tablas (correrlo después de cada db:push)
pnpm db:sedes       # crea institucion_sedes y busquedas.sede_id y da a cada institución su sede principal (aditivo, se puede correr de nuevo)
pnpm db:planes      # crea las tablas planes y planes_condiciones (con RLS) y las llena con los valores de lanzamiento; no pisa lo que ya se editó (aditivo, se puede correr de nuevo)
pnpm db:storage     # crea los buckets de Storage
pnpm db:setup       # push + rls + storage + seed, de una
pnpm db:admin --email=<correo> [--rol=institucion]   # da (o quita) el rol admin: entra a /backoffice
pnpm db:vincular --institucion=<correo> --docente=<correo>   # liga cuentas reales de Supabase con los datos demo (rehacer tras cada db:seed)
pnpm db:seed        # catálogos + datos demo (es_demo=true); --solo-catalogos / --borrar-demo
pnpm db:limpiar-archivos [--borrar] [--horas=24] [--usuario=<uuid>]   # lista (y con --borrar elimina) los archivos de Storage que ninguna fila usa
vercel env pull .env.local --yes   # trae las variables de Supabase
```

Las reglas puras (facturación, CSV de contactos, tipos y paths de archivos, validaciones de fechas) tienen su prueba al lado del módulo (`algo.test.ts`): al tocarlas, correr `pnpm test` y sumar el caso que corresponda; si una regla nueva no toca base ni Next, escribirla como función pura para poder probarla así. Lo que toca base, Storage o pantallas se prueba a mano en el navegador.

Las variables viven en `.env.local` (no se commitea). `drizzle-kit` y `tsx` no cargan `.env.local` solos: los scripts `db:*` ya usan `dotenv`.

### Conexión a la base

La app se conecta por el **pooler de sesión** de Supabase (`DATABASE_URL`, puerto 5432, host `*.pooler.supabase.com`, que funciona por IPv4). **No usar el pooler de transacciones (6543)** para la app: con `postgres-js` y Next las consultas se traban de forma intermitente al reutilizar conexiones (lo medimos: 60 s de cuelgue, sesiones "active / ClientRead" que no terminan). La conexión directa (`db.<ref>.supabase.co`) es solo IPv6 y no sirve en redes IPv4 ni en Vercel. El límite lo pone el tamaño del pool de Supabase (por defecto 15 conexiones de servidor, compartidas por todas las instancias de Vercel, también las viejas tras un redeploy): si se agota, las páginas con varias consultas fallan con `EMAXCONNSESSION`. Por eso en Vercel cada instancia usa 2 conexiones (`maxConexiones()` en `src/db/index.ts`, ajustable con `DB_POOL_MAX`) y conviene subir el "Pool Size" en el panel de Supabase. `/api/salud` muestra el estado: variables presentes y si la base conecta, con el código del error.

### Seguridad con Supabase

- La app **no usa la API REST de Supabase para datos**: se conecta directo a Postgres (rol `postgres`, que saltea RLS) desde el servidor. Por eso todas las tablas llevan **RLS activado sin políticas** (`pnpm db:rls`): la clave pública (anon) que viaja al navegador no puede leer ni escribir nada. Una tabla nueva sin RLS queda expuesta: correr `db:rls` después de cada `db:push`.
- La **clave de servicio** (`SUPABASE_SERVICE_ROLE_KEY`) solo se usa en servidor (`src/lib/supabase/admin.ts`); jamás con prefijo `NEXT_PUBLIC_`.
- `usuarios.id` es el uuid de `auth.users`. La sesión se valida con `getClaims()` (JWT) en `src/proxy.ts` y `src/lib/auth.ts`.
- Archivos: las subidas pasan por `/api/subir` (servidor); `publico` se lee por URL pública, `privado` (CV, documentos) solo con URL firmada generada en el servidor.
  - Vercel corta los pedidos de más de ~4,5 MB (`FUNCTION_PAYLOAD_TOO_LARGE`, medido en producción). Por eso el navegador achica las imágenes (hasta 3 intentos de calidad) y los **PDF de más de 4 MB (hasta 10) se suben directo a Storage con una URL firmada**: `/api/subir/firmar` da la URL de una carpeta de paso (`<usuario>/subidas/`), el navegador sube, y `/api/subir/confirmar` mira que sean los bytes de un PDF, que pese lo permitido y que sea de esa cuenta, y recién ahí guarda **esos mismos bytes** en su carpeta definitiva y borra el de paso (si no, lo borra). No se mueve el original porque Storage puede seguir sirviendo una copia vieja de un path ya tocado (se vio en pruebas). Así ningún archivo sin revisar llega a un path que las acciones acepten. Lo que no se confirma queda en `subidas/` hasta que `db:limpiar-archivos` lo barre.
  - Las imágenes que van al bucket `publico` se vuelven a codificar siempre en el navegador: se les saca el EXIF (puede traer el lugar donde se sacó la foto y esas URLs son públicas) y se limitan a 2000 px. Las del `privado` (documentos) se suben tal cual.
  - Los archivos reemplazados o quitados se borran de Storage al guardar: `borrarArchivos(quitados(antes, despues))` (`src/lib/queries/archivos.ts`), que corre después de guardar con éxito, no rompe la acción si falla y no borra un archivo que otra fila siga usando. Una acción nueva que guarde archivos tiene que llamarla, y la columna nueva sumarse a `estaEnUso`.
  - Lo que quedó huérfano igual (subidas abandonadas, o anteriores a esto) se limpia con `pnpm db:limpiar-archivos`: por defecto solo muestra qué borraría; `--borrar` borra. Mira toda la base (no una lista de columnas) y respeta un margen de 24 h para no tocar subidas en curso.
  - Documentación del docente (`docente_detalle.documentos`: `dniFrente`, `dniDorso`, `credencial`, `constancia` (de quien estudia, ver "Profesionales que todavía estudian"), `conducta`, todo en `privado`): se sube en el alta o después desde `/docente/perfil#documentacion` (`actualizarPerfilDocente`). Subir algo nuevo mientras está en `correccion` lo devuelve a `pendiente`, y si queda en revisión avisa a los admins (`avisarAAdmins`). Con la verificación hecha (DNI) o el título verificado no se puede cambiar desde el perfil, y con la verificación rechazada solo queda el certificado: el equipo lo resuelve por Contacto.
  - **Verificar borra las fotos del DNI:** al verificar (`aplicarVerificacion`, `src/lib/backoffice-docentes-escrituras.ts`) se quitan `dniFrente` y `dniDorso` de `docente_detalle.documentos` en la misma transacción y la acción (`verificarDocente`) las borra de Storage con `borrarArchivos` **después** de confirmar (si el borrado falla queda como huérfano para `db:limpiar-archivos`; la verificación no se deshace). Se conserva el **número** de DNI (y el CUIL) como constancia; título y certificado de conducta no se borran. La auditoría `docente.verificar` anota `dniBorrado`. Una verificación ya hecha deja el DNI como "Validado · fotos borradas" en la ficha y no lo cuenta como faltante (`faltantesDe`); si algún día se revierte una verificación, la persona tiene que volver a subir el DNI. Rechazar o pedir corrección NO borra nada (la persona puede estar corrigiéndolo). `/privacidad` lo dice: si cambia esta regla, actualizarla.
  - **Nombre y apellido del profesional:** hasta que el equipo verifica el DNI se editan en Mi perfil (dos campos con etiqueta, no un título sin borde: así no se notaba que se podían tocar); con `verificacion = verificado` quedan **fijos** (`identidadFija`, `src/lib/perfil-docente.ts`, con prueba): Mi perfil los muestra como texto con el motivo y el enlace a Contacto, y el servidor lo exige (`actualizarPerfilDocente` rechaza un nombre distinto y nunca lo escribe; `guardarDatosDocente`, el alta, también lo conserva). Hoy solo se corrigen a mano en la base: no hay pantalla del backoffice para eso.

## Principio rector: nada hardcodeado

Todo lo que el prototipo tenía en el `state` inicial (instituciones, ofertas, postulantes, cursos, notificaciones, equipo, testimonios, zonas, asignaturas) sale de la base. Los datos de ejemplo están en `src/db/seed-data.ts`. Solo son constantes en código los **vocabularios cerrados** (`src/lib/catalogo.ts`: niveles, turnos, tipos, etapas, roles, colores de categoría).

### Reglas

1. **Lecturas** en `src/lib/queries/<dominio>.ts` (`import "server-only"`, siempre `getDb()`, nunca un cliente de base en el navegador). Las páginas son Server Components y llaman a las queries directo.
2. **Escrituras** solo en server actions (`src/app/actions/<dominio>.ts`, `"use server"`). Cada acción: (a) obtiene al usuario con `requerirUsuario`/`requerirInstitucion`/`requerirDocente`, (b) **verifica que el recurso le pertenece** (una institución solo toca sus búsquedas/postulaciones; un docente solo las suyas), (c) valida con Zod (`parsear`), (d) devuelve `Resultado`, (e) llama a `revalidatePath` de lo que cambió. Nunca confiar en un id que venga del cliente sin chequear propiedad.
3. **Notificaciones**: toda acción relevante (postulación nueva, invitación, cambio de etapa, entrevista, oferta, contratación, verificación) crea una con `notificar()` (`src/lib/queries/notificaciones.ts`) para quien corresponda.
4. **Interactividad**: Client Components solo donde hay estado de UI (drag & drop del kanban, filtros en vivo, drawers, mapa). Filtros que cambian el listado → querystring (`searchParams`) para que la URL sea compartible; los controles lo actualizan con `useRouter`/`<Link>`.
5. **Formularios**: `<form action={…}>` con `useActionState`; errores por campo con `Campo error={…}`. Sin estado local duplicado de lo que ya está en la base.
6. **Identidad**: la fila `usuarios` se crea en el onboarding (`asegurarUsuario(rol)`), no con un trigger ni un webhook. El rol decide el área; `admin` entra a todo.
7. **Distancias**: nunca "km" fijos; se calculan con `distanciaKm` (`src/lib/geo.ts`) entre el docente y la institución (o el curso presencial).
8. **Direcciones**: todo formulario que pide una dirección usa `<CampoDireccion>` (`src/components/ui/campo-direccion.tsx`): ubica sola la dirección mientras se escribe y completa partido y provincia. Ver "Ubicación automática de direcciones".

### Ubicación automática de direcciones

Al escribir una dirección, `<CampoDireccion>` pide sugerencias a `GET /api/ubicacion` (exige sesión, tope de 40 consultas por minuto por cuenta). **Georef** (`apis.datos.gob.ar/georef`, API oficial, sin clave) va primero; **OpenStreetMap/Nominatim** solo de respaldo (1 pedido por segundo desde el servidor, con `User-Agent`, y la atribución a OSM se muestra cuando el resultado es de ahí). Georef es exacto cuando conoce la calle pero flojo con localidades (Nordelta, Mar del Plata); Nominatim al revés. Un resultado solo sirve si coincide con lo escrito: lo que viene después de la primera coma ("Av. Maipú 1234, Vicente López") tiene que aparecer en el partido, la localidad o la provincia (`coincidenPistas`); si no hay pistas, la persona elige entre las opciones de distintos lugares.
- **El servidor no le cree coordenadas al navegador.** Cada sugerencia vuelve con una firma HMAC (`firmarUbicacion`, secreto `CORREO_SECRETO` o, si no, `SUPABASE_SERVICE_ROLE_KEY`; vale 6 h y está atada al texto de la dirección). El formulario la manda en el campo oculto `ubicacion` (o en el estado, en la vitrina) y `ubicarPorDireccion` (`src/lib/queries/ubicacion.ts`, reglas en `ubicarEntrada`) la acepta solo si es suya, reciente, de esa misma dirección y sin contradecir el partido que quedó escrito; si no, busca él y toma el primer resultado que coincide; si nada coincide, se usa el catálogo de zonas como antes (`ubicarInstitucion`).
- **Dónde se usa:** alta de institución (lat/lng; la `zona` sale del catálogo si la hay, si no de la localidad encontrada), perfil público (`ubicacionDeLaVitrina`: solo re-ubica si la dirección cambió o faltaban coordenadas; ahí sí actualiza partido y provincia), cursos presenciales (`cursos.lat/lng/partido/provincia`, `ubicacionDeCurso`; el docente ve "a X km" en la tarjeta y el detalle) y el alta del docente.
- **El domicilio del docente es privado:** `proposito: "docente"` consulta **solo Georef** (nunca OSM), no guarda nada en el caché y solo completa partido y provincia en el formulario; su lat/lng siguen saliendo de las zonas de trabajo (no se usa el domicilio para los km).
- Georef/OSM caídos o sin resultado no bloquean nada: se avisa "No encontramos esa dirección…" y se completa a mano. Las pruebas están en `src/lib/ubicacion.test.ts` (fixtures con la forma real de las dos APIs). Si se toca esto, correr `pnpm test`.

### Respuesta a la entrevista ("Voy" / "No puedo")

Cuando la institución agenda una entrevista, el profesional puede responder **Voy** o **No puedo** (con un mensaje opcional, p. ej. otro día que le quede bien) desde el cajón de Mis postulaciones (`RespuestaEntrevista`, acción `responderEntrevista` en `actions/postulaciones.ts`). Columnas `postulaciones.entrevista_respuesta` (`voy` / `no_puedo`), `entrevista_respuesta_en` y `entrevista_respuesta_mensaje`, agregadas a mano con **`pnpm db:entrevista`** (aditivo e idempotente: correrlo **antes** de desplegar el código que las usa). Reglas puras en `src/lib/entrevista-respuesta.ts` (con prueba).
- **El mail M24 no responde solo:** sus botones "Voy a ir" / "No puedo ir" abren la postulación con `?entrevista=voy|no-puedo`, que solo preselecciona; la respuesta se manda con un toque en la app, con la sesión abierta (como `/auth/confirmar`: un antivirus que abre los enlaces del mail no la gasta).
- La acción relee la fila bloqueada y exige que la fecha que la persona estaba viendo (`para`) siga siendo la vigente: si la institución la cambió en el medio, pide mirar la nueva. Solo se responde una entrevista futura, de una postulación no archivada y con la búsqueda abierta; se puede cambiar la respuesta hasta que pase.
- **Reprogramar o quitar la entrevista borra la respuesta** (`agendarEntrevista`, `quitarEntrevista`).
- La institución recibe un aviso en la campanita (sin mail) y ve la respuesta en la tarjeta del tablero ("confirmó ✓" / "No puede ir: reprogramá") y en la ficha del postulante, con el mensaje.

### Etapa "Examen preocupacional"

Etapa nueva del tablero (`examen_preocupacional`), **después de Oferta y antes de Contratados**: la institución la usa si pide el estudio médico para ingresar a trabajar; si no la usa, no pasa nada. En la ficha del postulante (`cajon-postulante.tsx`) hay un checklist "Para ingresar a trabajar" con "Hizo el examen preocupacional" (`marcarExamenPreocupacional`, `postulaciones.examen_preocupacional_en`; solo se puede tildar mientras la persona esté en esa etapa). La institución también puede **adjuntar los archivos del estudio** (hasta 5, PDF o foto): `agregarArchivoExamen` / `quitarArchivoExamen`, columna jsonb `examen_preocupacional_archivos` (`{path, nombre}`), carpeta `examenes` del bucket privado (`src/lib/examen-preocupacional.ts`); se pueden sumar y quitar mientras esté en la etapa o ya contratada. **Es información de salud (dato sensible)**: solo bucket privado, **nunca una URL en la página**; se abre con `/api/examen-preocupacional/<postulación>/<n>`, que verifica que la cuenta sea de la institución dueña y redirige a una URL firmada de 1 minuto. El docente **no** los ve (solo "pendiente / realizado"). Cualquier lugar nuevo que muestre esos archivos tiene que pasar por esa ruta. Tema para la revisión legal de `/privacidad`.
- **El docente** recibe un aviso en la campanita al pasar a la etapa (`avisoDeEtapa`; **sin mail**, no hay plantilla) y ve "Examen preocupacional pendiente / realizado" en Mis postulaciones (`estadoParaDocente(etapa, estadoBusqueda, examenRealizado)`: todo lugar que lo llame con una postulación tiene que pasar el tercer parámetro).
- **Contratar** pide confirmar (casilla "Contratarla igual, sin el examen", `faltaExamenPreocupacional`) solo si la persona está en esa etapa y falta el examen; el servidor lo vuelve a exigir.
- La columna del tablero sale de `ETAPAS` (`src/lib/catalogo.ts`); una etapa nueva también va en `ETAPAS_MOVIBLES`, `ETAPA_MENU`/`COLOR_ETAPA`/`INSIGNIA_ETAPA` (`src/lib/pipeline.ts`), el `COLUMNA_VACIA` del tablero y los dos `TONO_ETAPA`. El valor del enum y la columna se agregaron a mano en la base (`alter type … add value`, `alter table … add column`).

### Profesionales que todavía estudian

En el alta, "Estoy estudiando" (`docente_detalle.situacion_estudio = 'estudiante'`) pide el **porcentaje de materias aprobadas** (`porcentaje_materias`, entero 0–100; columna agregada a mano en la base) y, en lugar del título, la **constancia de alumno regular** (`documentos.constancia`, bucket `privado`, **obligatoria**). Las reglas puras (leer el porcentaje, la etiqueta "Estudiante · 80 % de la carrera", qué cambios de estudios se aceptan desde Mi perfil) están en `src/lib/estudiantes.ts` con sus pruebas.
- **Las instituciones lo ven** (decisión de producto): insignia "Estudiante · N %" en la tarjeta del buscador, en el perfil del profesional y en el cajón del tablero de postulantes (`estudiantesEntre`, `src/lib/queries/estudiantes.ts`, lee solo esas dos columnas de `docente_detalle`). Donde otros muestran "Título", el estudiante muestra "Constancia de alumno regular" (con tilde si el perfil está verificado). **La página pública de "Compartir mi perfil" no lo muestra** a propósito.
- **Verificación:** la constancia se revisa junto con el DNI. En la cola, para un estudiante hay que tildar "Revisé la constancia de alumno regular" (además del DNI) y **verificar nunca marca el título** (`aplicarVerificacion` fuerza `tituloVerificado = false`). Las constancias no se borran al verificar (los DNI sí).
- **Mi perfil** (`actualizarPerfilDocente`, sección "Tus estudios"): se puede pasar de "Estoy estudiando" a "Ya me recibí" (se quita la constancia, se borra de Storage, se deja de guardar el porcentaje y aparece la fila del título) y actualizar el porcentaje cuando se quiera, también con el perfil verificado. **No** se puede volver a "estudiando" con el perfil verificado ni cambiar nada con la verificación rechazada (`decidirEstudios`): se escribe al equipo por Contacto. Cambiar la constancia con el perfil verificado tampoco se puede, igual que el DNI.
- **Quien se recibe después de verificado:** sube el título desde Mi perfil, el equipo recibe el aviso (campanita + M61 "subió su título para que lo revisen") y lo valida con el botón **"Verificar título"** de la ficha del backoffice (`verificarTitulo` → `aplicarVerificacionDeTitulo`, auditoría `docente.verificar_titulo`, aviso en la campanita sin mail). Solo toca el título: identidad y antecedentes quedan como estaban.
- El porcentaje es un dato **declarado**: no se revisa de nuevo cuando se actualiza.

### Invitaciones al equipo

Invitar (Equipo, solo dueño y administradores) crea una fila `institucion_miembros` en estado `invitado` con el email y el rol, y encola el mail M06 cuyo enlace es **`/invitacion/<id de la invitación>`** (`rutaDeInvitacion`, `src/lib/equipo.ts`). Esa página pública (`src/app/invitacion/[id]/page.tsx`) muestra a qué institución y con qué rol se invitó y trae el **email puesto y fijo**: la persona crea su contraseña, confirma el mail y entra directo al equipo (el paso 2 del alta llama a `institucionComoMiembro`, que la une por el email y avisa al resto). Sin Google a propósito (tiene que ser el email invitado; con otro se terminaría creando una institución). **Los términos:** quien llega invitado se salta el paso 2 (donde las instituciones los aceptan), así que el formulario de la invitación trae la casilla (manda `conTerminos` y `registrarse` deja la constancia en `user_metadata`, como el docente) y, **pase lo que pase, `institucionComoMiembro` no activa una invitación si `usuarios.terminos_aceptados_en` es null** (`puedeSumarseAlEquipo`): en ese caso el paso 2 muestra "Sumate al equipo de X" (`UnirseAlEquipo`, acción `unirseAlEquipo`) para aceptarlos y recién ahí entra. Quien ya tiene cuenta de institución con ese email solo ingresa. Con la sesión de otro email la página lo avisa; si la invitación ya no existe (se usó o se canceló) lo dice. **Unirse siempre se decide por el email verificado de la sesión, nunca por el enlace**: el id solo sirve para mostrar la invitación. Los roles hoy **solo se hacen cumplir** para invitar/quitar gente, editar el perfil público y manejar el plan (`esRolGestor`); el resto de las descripciones de `ROLES_EQUIPO_INFO` (p. ej. "no publica ni contrata") es texto, no un permiso.

### Sedes de las instituciones

Una institución es una organización (nombre, CUIT, plan, equipo, perfil público) con **una o más sedes** (`institucion_sedes`: nombre, dirección, partido, provincia, zona, lat/lng, CUE y `es_principal`). Toda institución tiene siempre **una sede principal** (índice único parcial). Las reglas puras están en `src/lib/sedes.ts` con sus pruebas; la tabla y `busquedas.sede_id` se crearon a mano con **`pnpm db:sedes`** (aditivo e idempotente: da a cada institución su "Sede principal" con la ubicación que tenía y asigna sus búsquedas; **correrlo de nuevo** si aparecen instituciones o búsquedas sin sede, p. ej. creadas por código viejo antes de un deploy). Una tabla nueva sigue necesitando `db:rls`.
- **La sede principal es la fuente de verdad; las columnas de ubicación de `instituciones` (dirección, partido, provincia, zona, lat, lng y CUE) son un espejo.** Nada más debe escribirlas: `guardarSedePrincipal` / `sincronizarEspejo` (`src/lib/queries/sedes.ts`) las actualizan en el mismo paso (alta, guardado de sedes, backoffice). Lo que habla de "la institución" en general (listados, factura —el domicilio del comprobante es el de la principal—, ficha) sigue leyendo el espejo.
- **Lo que depende de DÓNDE es una búsqueda lee su sede** (`busquedas.sede_id`; `lugarDeBusqueda(sede, institucion)`: sin sede —búsquedas viejas, o la sede se borró cuando ya estaba cerrada— cae en la institución, o sea la principal; una sede sin ubicar NO cae en otra, sus km quedan sin calcular). Es el caso de los kilómetros, el mapa, la dirección y la zona de las ofertas (lista, detalle, inicio, Mis postulaciones, calendario de la entrevista) y los km del tablero de postulantes. Una búsqueda es de **una** sede; la zona de la búsqueda (`busquedas.zona`, texto) arranca con la de la sede y sigue editable para sumar linderos. Al publicar o editar se elige la sede solo si hay más de una (`sedeParaBusqueda` valida que sea de la institución).
- **Numeradas y en su propia pantalla (pedido de Richi, 2026-10-15):** las sedes se muestran numeradas (la principal es la 1 y el resto por nombre: `numerarSedes`, `src/lib/sedes.ts`; el número no se guarda, sale de `ordenarSedes`) en el editor, al publicar y en los perfiles (`ListaDeSedes`). La institución las edita en **`/institucion/sedes`** (ítem "Sedes" del menú); "Mi perfil" solo lleva un enlace ahí.
- **Publicar en varias sedes a la vez:** al **crear** una búsqueda con más de una sede se marcan una o varias (tarjetas numeradas, campo `sedeIds`); `crearBusqueda` valida con `sedesElegidas` (solo sedes propias, sin repetidas, hasta `MAX_SEDES_POR_PUBLICACION` = 10) y crea **una búsqueda igual por sede**, cada una con la zona de su sede. A cada profesional se le avisa **una sola vez por publicación** (por la primera sede en la que encaja). Al **editar**, la búsqueda sigue siendo de una sola sede.
- **Editor "Sedes"** (`SedesFormulario`, en `/institucion/sedes` y en la edición del backoffice): se guarda la lista completa (`guardarSedesDeInstitucion`, `src/lib/queries/sedes-guardar.ts`; la institución por `actualizarSedes`, el equipo por `actualizarSedesComoAdmin`). Cada dirección nueva o cambiada se ubica de nuevo con la misma firma de ubicación de siempre (el servidor no le cree coordenadas al navegador). **No se puede quitar la principal sin marcar otra ni una sede con búsquedas abiertas o pausadas**; las cerradas quedan sin sede. **El CUE es de cada sede y solo lo carga el equipo** (la institución lo ve en blanco y el servidor lo conserva).
- **Buscar profesionales** mide la cercanía desde la sede de la búsqueda elegida o, sin búsqueda, desde todas las sedes ubicadas (cada profesional, a la más cercana: `puntosDeReferencia`, `sedeMasCercana`; la tarjeta dice "a 5 km de Sede Pilar" cuando hay varias). Los profesionales recomendados del inicio juntan las zonas de todas las sedes. **Tablero de postulantes:** la lista de búsquedas se filtra por sede (`?sede=`) cuando hay varias.
- **Catálogo y perfiles:** una sola página por institución con todas sus sedes (`ListaDeSedes`, `SedePublica` —**nunca el CUE ni el id**: se arma campo por campo en `aSedePublica`—); la tarjeta dice "N sedes", el filtro de zona encuentra la institución si **cualquier** sede está ahí y el mapa pone un pin por sede. Las búsquedas abiertas dicen en qué sede son cuando hay más de una. Backoffice: la ficha lista las sedes con su CUE y el listado busca por la zona de cualquiera.
- El precio es **por institución** (no hay costo por sede) y el equipo no se restringe por sede: todos ven todo. El horario de administración, las fotos y los topes siguen siendo por institución.
- **Sin pruebas automáticas** (usan la base): las cuentas de km y coincidencias por sede, el SQL del buscador con varias sedes y el filtro del tablero. Se verificaron a mano con una institución de ejemplo de dos sedes (dato de prueba que se borró después). El seed (`db:seed`) crea solo la sede principal de cada institución de ejemplo.

### Editar una institución desde el backoffice

El equipo (rol `admin`) edita el perfil de cualquier institución desde su ficha (`/backoffice/instituciones/<id>`, botón "Editar perfil" → `/editar`). La pantalla reutiliza el formulario de "Perfil público" de la institución (`VitrinaFormulario` con `institucionIdAdmin`: guarda por `actualizarVitrinaComoAdmin` y los textos y enlaces dejan de hablarle a la institución) y suma el editor de **Sedes** (con el CUE de cada una, que solo carga el equipo) y la tarjeta "Datos de la cuenta" (`DatosDeCuentaFormulario`, acción `actualizarDatosDeInstitucion`: teléfono y CUIT, que la institución no edita sola). Ver "Sedes de las instituciones".
- **El guardado de la vitrina es uno solo para las dos puertas:** `guardarVitrinaDeInstitucion` (`src/lib/queries/vitrina-guardar.ts`) valida, ubica la dirección, guarda y borra de Storage lo reemplazado. `actualizarVitrina` (institución, exige `esRolGestor`) y `actualizarVitrinaComoAdmin` (admin, por el id que se le pasa, validado como uuid) solo deciden QUIÉN edita y DE QUÉ institución; una regla nueva de la vitrina se escribe ahí, una vez.
- **Dos personas editando a la vez no se pisan:** el perfil público y las sedes llevan una **huella** de lo que la pantalla estaba viendo (`huellaDeVitrina`, `src/lib/vitrina.ts`; `huellaDeSedes`, `src/lib/sedes.ts`; con pruebas), que viaja junto con el resto al guardar. `guardarVitrina` y `guardarSedesDeInstitucion` la comparan, **dentro de la transacción y con la fila de la institución bloqueada**, con lo que hay en ese momento: si no coincide, no se escribe nada y se avisa ("Otra persona del equipo guardó cambios… recargá la página") como ya hace Planes. Después de guardar devuelven la huella nueva y la pantalla la usa para el siguiente guardado. En sedes el CUE solo entra en la huella de quien puede cargarlo (si no, un cambio del equipo le daría un conflicto falso a la institución) y la ubicación en el mapa no entra (sale de la dirección). Una acción que llegue sin huella (un navegador viejo) guarda como antes. Un campo nuevo de la vitrina se suma a `CAMPOS_DE_VITRINA` y entra solo en la huella.
- Las imágenes nuevas tienen que ser de las que subió **la cuenta que guarda**: el admin sube las suyas por `/api/subir` (carpeta `<admin>/…`) y `esUrlPublicaPropia(url, quienSube)` las acepta.
- **Auditoría, sin aviso:** `institucion.editar_perfil` / `institucion.editar_datos` / `institucion.editar_sedes` con los **nombres** de los campos tocados (`cambiosDeVitrina`, `src/lib/vitrina.ts`), nunca los valores; se ven en "Actividad del equipo" (`describirAccion`). No se le avisa a la institución (ni campanita ni mail), a diferencia de verificar o cambiar el plan. Si no cambió nada no se anota nada.

### Altas sin terminar (backoffice)

Pantalla `/backoffice/altas-sin-terminar` (menú "Altas sin terminar", solo admin). Hay cuentas que se registran y nunca terminan el alta: no tienen "Mi cuenta" desde donde pedir la baja y la lista de profesionales solo muestra altas completas (`EXISTE_CON_ALTA`), así que el equipo las ve y las borra desde acá. Reglas puras en `src/lib/cuentas-sin-terminar.ts` (con prueba), consultas y borrado en `src/lib/queries/cuentas-sin-terminar.ts`, acción `borrarCuentaSinTerminar` (`src/app/actions/backoffice-cuentas.ts`).
- **Dos listas, solo de quienes se registraron hace más de 24 horas** (`HORAS_MINIMAS_SIN_TERMINAR`: el servidor también lo exige, porque puede ser alguien completando el alta en este momento): quienes **eligieron un rol y no siguieron** (fila `usuarios` de profesional o institución sin perfil completo, sin institución propia ni equipo; incluye al profesional que empezó el perfil y lo dejó a medias, con su DNI y documentos) y quienes **se registraron y nunca entraron al alta** (solo existen en `auth.users`, que se lee con SQL directo). Muestra en qué punto se quedó cada uno.
- **Borrar** pide escribir el email de la cuenta. Borra de verdad y no se puede deshacer: si había empezado el perfil, lo borra como la baja de un profesional (`borrarDatosDelProfesional`); si no, su fila `usuarios` (con los avisos y favoritos en cascada), los mails (`cola_correos`) y mensajes de Contacto a su email y el detalle de la auditoría sobre la cuenta; después, Storage y el usuario de Supabase Auth, con la misma regla de "base primero, y si algo falla se lo dice al admin y anota `cuenta.baja_incompleta`". Anota `cuenta.sin_terminar_borrada` sin datos personales. Nunca borra una cuenta admin, ni de ejemplo, ni una con el alta completa (esas se dan de baja desde su ficha), ni la propia.
- Se probó contra la base real en una transacción que se deshizo (con una cuenta de cada tipo, incluida una cuenta de acceso creada en `auth.users` solo para la prueba).

### Baja de una institución

"Procesar baja" (ficha de la institución en el backoffice, solo admin, `procesarBajaInstitucion` en `src/app/actions/backoffice-instituciones.ts`, lógica en `src/lib/queries/baja-institucion.ts`, reglas puras en `src/lib/baja-cuenta.ts` con prueba). **No se puede deshacer.** A diferencia de la baja de un profesional (que borra todo), acá se **conserva lo fiscal**: el registro de la institución con nombre, tipo, CUIT, condición fiscal y domicilio (más el plan y el día de cobro) y **todas sus facturas**. Se pide escribir el nombre exacto de la institución y el servidor lo vuelve a exigir; el diálogo muestra los números de lo que se lleva y de lo que queda, y avisa si hay facturas sin pagar (la deuda no se borra).
- **Se borra, en una transacción:** el equipo (miembros e invitaciones) y las cuentas de acceso de la dueña y del equipo (`cuentasDelEquipoParaBorrar`: solo las de rol `institucion`, nunca una cuenta admin ni la de quien procesa), las búsquedas con sus postulaciones y notas, los cursos con sus inscripciones, los CV enviados, los contactos privados, las novedades, la galería, los pedidos de plan, las sedes menos la principal (que queda con el domicilio y sin ubicación ni CUE), los avisos que llevan a la institución o a sus búsquedas, los mails (`cola_correos`) y mensajes de Contacto de su equipo, los favoritos, y el `detalle` de la auditoría anotada sobre ella. El registro queda con `slug = baja-<id>`, sin dueña, sin verificar y `suspendida = true`.
- **Después de confirmar la base:** se borran de Storage las imágenes públicas (logo, portada, galería, fotos de cursos), los estudios del examen preocupacional y todo lo de `<usuario>/…` de cada cuenta, y por último los usuarios de Supabase Auth. Si algo de eso falla, la base ya quedó limpia: se lo dice a quien procesa y anota `cuenta.baja_incompleta` (`pnpm db:limpiar-archivos --borrar`; usuarios en Supabase → Authentication → Users).
- **Quedó marcada con `instituciones.baja_en`** (columna agregada a mano: `alter table instituciones add column if not exists baja_en timestamptz`; hay que correrla en una base nueva antes de desplegar). Las acciones del backoffice (`institucionBloqueada`, editar perfil, sedes, datos de la cuenta) tratan una dada de baja como inexistente y la ficha no ofrece suspender, reactivar, plan ni editar: **no se reactiva**; si vuelve, se crea una cuenta nueva. El listado tiene el estado "Dadas de baja". Una factura se sigue pudiendo cobrar o anular desde Cobros.
- La probó contra la base real en una transacción que se deshizo (con una institución de prueba completa: equipo, cuentas, búsquedas, postulación con examen, curso, contactos, facturas, avisos, mails, favoritos y auditoría). `/privacidad` y el texto de "Darse de baja" de la institución lo explican: si cambia lo que se borra o se conserva, actualizarlos.

### Compartir mi perfil (profesional)

En Mi perfil (`/docente/perfil`) la tarjeta "Compartir mi perfil" (`PerfilCompartir`) tiene un interruptor, **apagado por defecto**. Prendido, el perfil tiene página pública en **`/profesional/<token>`** (`src/app/(publico)/profesional/[token]/page.tsx`, sin sesión) y la tarjeta ofrece copiar el enlace, mandarlo por WhatsApp y verlo.

La institución que la abre ve botones para ingresar o crear cuenta; el contacto se habilita por el camino de siempre (postulación, CV enviado o invitación). No se avisa ni se cuentan las visitas.
- `/privacidad` lo describe: si cambia lo que muestra la página, actualizarla.

### "Buscá con IA" (buscador de profesionales)

La frase libre ("profe de inglés para secundario, turno mañana") se convierte en filtros con `interpretarBusqueda` (`src/lib/busqueda-ia.ts`, **función pura con pruebas**, se llama en el servidor leyendo `?q=`). **No hay ningún modelo detrás y no cuesta nada**: es reconocimiento de palabras, y Flor decidió no pagar API de IA por ahora ([[lectura-cv-pospuesta]] en la memoria). Entiende sinónimos (`ALIAS_DISCIPLINA`: gimnasia → Educación Física, pileta → Natación; un alias solo vale si la disciplina existe en el catálogo), errores de tipeo (distancia de edición: 1 letra desde 5 letras, 2 desde 11; las palabras cortas no se corrigen y `RELLENO` evita que "tenés" sea Tenis), niveles escritos de varias formas ("1° grado", "sala de 4"), zonas y grupos (`ALIAS_ZONA`: capital → CABA, zona norte → Vicente López, San Isidro y Tigre, solo los que existan en el catálogo) y devuelve `sinEntender`: las palabras que no pudo convertir en filtro, que la barra muestra como "No pudimos aplicar como filtro: «noche»". Un filtro nuevo se suma ahí y su prueba en `busqueda-ia.test.ts`. Pensada para reemplazarse por un modelo real sin cambiar la forma `{ filtros, leido, reconocido, sinEntender }`. Si la frase nombra varias materias, quedan en el orden en que se escribieron.

**Lo mismo para el profesional que busca trabajo** (`Oportunidades`, `Búsquedas rápidas` y la pública `/buscar-trabajo`): la caja "Buscá con IA" de `ControlesBuscador` navega a `?frase=…` y `filtrosConFrase` (`src/lib/queries/oportunidades-frase.ts`) la convierte en `FiltrosOportunidades` con `leerFraseDeTrabajo` (`src/lib/oportunidades-ia.ts`, pura, con prueba) usando `interpretarBusqueda(..., { buscaTrabajo: true })`, que lee los turnos como los de una oferta (`TURNOS`: Mañana, Noche, Fin de semana…). Una frase reemplaza los filtros de la URL; al tocar un filtro después, la URL se arma desde los filtros y la frase no viaja (manda el ajuste manual). Solo se aplica lo que esa pantalla sabe filtrar: una sola materia (`q`; con más se avisa del resto), una sola zona **no** (la distancia sale del perfil: «olivos» se avisa en vez de ignorarse), favoritos solo con cuenta. Se sumó el filtro **`tipo`** (Titular, Suplencia, Temporada, Freelance; "Suplencia" incluye las rápidas) a la búsqueda de ofertas y a sus controles. **Las tres pantallas se ven igual** (2026-10-16): la pública `/buscar-trabajo` usa el mismo panel de filtros (`PanelFiltrosApp`), la misma caja "Buscá con IA" y las mismas tarjetas (`TarjetaOfertaApp`, con "Postularme" para quien no tiene cuenta) que el área del profesional; con `publico` solo faltan la distancia y los favoritos. Ya no hay un panel viejo: un control nuevo del buscador se hace una sola vez, en `controles-buscador.tsx`.

**No se guarda nada de lo que la gente escribe en el buscador:** ni la frase ni las palabras que no entendió (se evaluó contarlas para ver qué sinónimos faltan y Flor prefirió no hacerlo). Lo que no se pudo aplicar solo se le muestra a quien buscó (`sinEntender`).

**Ayuda al publicar una búsqueda** (`FormularioBusqueda`): "Sugerir título / descripción / requisitos" aparecen mientras el campo está vacío y arman un texto de partida con lo ya completado (`src/lib/redaccion-busqueda.ts`, plantillas puras con prueba). **No inventan nada**: ni beneficios ni sueldos; los requisitos son los habituales de cada categoría y la institución los edita. Piden elegir antes la disciplina.

**Profesionales recomendados** (dashboard de la institución, `docentesRecomendados`): se puntúan con `puntuarCandidato` (`src/lib/recomendaciones.ts`, pura con prueba): disciplina de una búsqueda abierta (40), nivel y turno (8 y 8), cercanía (hasta 20), experiencia (hasta 10) y título verificado (5); el empate lo gana el más cercano. Cada uno muestra "por qué te lo recomendamos" (`motivos`, hasta dos). El dashboard le pasa las búsquedas activas (`BusquedaItem` ahora trae `nivel` y `turno`).

- **`src/lib/planes.ts` es puro** (sin base, sirve en servidor y navegador): la FORMA de los datos, los **valores de lanzamiento** (el respaldo si la base falla o le falta algo: `catalogoDesdeLaBase` completa campo por campo, así una fila rota nunca deja la app sin precios), `crearPlanes(catalogo)` con todas las reglas (`planDe`, `vigentes`, `clavesParaElegir`, `planPorTipo`, `tiposPorPlan`, `esMultisede`, `precioMultisede`, `packDe`, `precioDePlan`, `montoDePlan`, `nombreDePlan`, `equivalenteMensual`) y la validación de lo que se edita (`edicionDePlanesSchema`, `cambiosDePlanes`). Con prueba.
- **Cómo se usa:** en el servidor `const P = await planes()` (`src/lib/queries/planes.ts`, una lectura por pedido) y `P.montoDePlan(clave)`, `P.planDe(clave).label`…; un componente de cliente recibe `catalogo={P.catalogo}` por props y hace `crearPlanes(catalogo)`. **No importar precios ni nombres de plan fijos** (`PLANES` ya no existe): un lugar nuevo que muestre o calcule con un plan lee el catálogo. `planificarFacturas` recibe los planes como último parámetro (sin pasarlos, los de lanzamiento: así lo usan las pruebas).
- **Las claves son fijas** (`colegio`, `deportiva`, `multisede`, `fundador`, `estandar`, `anual`): las referencian instituciones y facturas, no se crean ni se borran planes desde la pantalla. `colegio` y `deportiva` no se pueden dejar de ofrecer (los reciben las instituciones nuevas según su tipo). Los planes anteriores (`vigente: false`) siguen editables porque hay cuentas que los tienen.
- **Un cambio de precio rige para lo que venga:** las facturas ya emitidas guardan su `monto` y no cambian; la factura del mes que se crea después (cron, "Cargar factura", pedidos de plan) sale con el precio nuevo, y la página pública, el plan de cada institución y el selector del backoffice lo muestran enseguida. Cambiar el precio de un plan heredado cambia lo que se les factura de ahí en más a las cuentas que lo tienen: la pantalla muestra cuántas instituciones tiene cada plan y pide confirmar con un resumen.
- **Guardar** (`guardarPlanes`, `src/app/actions/backoffice-planes.ts`, solo admin): valida de nuevo en el servidor, bloquea la fila de condiciones, compara con una **huella** de lo que se estaba viendo (si otra persona del equipo guardó mientras tanto, no pisa y pide recargar) y deja la auditoría `planes.editar` con los cambios (los precios llevan el valor de antes y de después; de lo demás solo qué campos se tocaron). "Últimos cambios" sale de ahí. Si no cambió nada, no se anota nada.
- **El mail M55/M56 y los avisos de cambio de plan** reciben el nombre ya resuelto (`P.nombreDePlan`); `describirAccion` toma los planes como parámetro opcional.
- **Sin pasarela de pago todavía** (ver "Pendiente"): editar un precio no cobra nada ni toca cuentas, solo cambia lo que se factura después.

### Cuenta, ingreso y registro

- **Mi cuenta** existe para docente (`/docente/cuenta`) e institución (`/institucion/cuenta`): email de acceso, contraseña, avisos por mail (interruptor `cambiarAvisosPorCorreo`) y pedido de baja. Contraseña y email son acciones de cualquier rol (`src/app/actions/cuenta.ts`). La baja, tanto de la institución (`actions/institucion.ts`) como del docente (`actions/cuenta.ts`), es un **pedido**, no un borrado: queda en auditoría (`cuenta.baja_solicitada`), avisa a los admins y la procesa el equipo a mano; la ficha del backoffice muestra "Baja solicitada".
- **Procesar la baja de un profesional (botón en su ficha del backoffice):** borra sus datos de verdad y **no se puede deshacer**. `procesarBajaDocente` (`actions/backoffice-docentes.ts`, solo admin; exige escribir el email de la cuenta, y funciona también sin que la persona haya pedido la baja) llama a `src/lib/queries/baja-docente.ts`: en **una transacción** relee y bloquea el perfil, valida (`impedimentoDeBaja`, `src/lib/baja-cuenta.ts`, con prueba: no a perfiles de ejemplo, sin cuenta, del equipo, de instituciones ni a uno mismo) y borra el perfil con todo lo que cuelga de él (postulaciones con sus notas, CV enviados, inscripciones, `docente_detalle` con DNI/CUIL/domicilio, documentos), los avisos y mails (`cola_correos`) que la nombran o llevan a su ficha, los mensajes de Contacto con su email, los favoritos que la guardan y su fila `usuarios`. De la auditoría **anula el `detalle`** de lo anotado sobre ella (llevaba nombre y email: queda qué, cuándo y quién) y deja `cuenta.baja_procesada` con solo números. **Después de confirmar la base** borra de Storage todo lo de `<usuario>/…` en los dos buckets más los estudios del examen preocupacional que las instituciones guardaron sobre sus postulaciones (viven en la carpeta de la institución), y por último el usuario de Supabase Auth. Si Storage o Auth fallan, la base ya quedó limpia: se lo dice al admin, anota `cuenta.baja_incompleta` y lo que falta se termina a mano (`pnpm db:limpiar-archivos --borrar`; usuario en Supabase → Authentication → Users). Las búsquedas por nombre (avisos y mails) solo se hacen con un nombre completo de 8 letras o más (`nombreParaBuscar`): con uno corto ("Ana") coincidiría con otras personas. **Las cuentas que nunca terminaron el alta no aparecen en la lista de profesionales (solo muestra altas completas): se ven y se borran desde "Altas sin terminar" (ver abajo).** **La baja de una institución tiene su botón** ("Procesar baja" en su ficha del backoffice, junto a suspender; no aparece en instituciones de ejemplo ni en las ya dadas de baja) y conserva lo fiscal: ver "Baja de una institución" abajo.
- **Cambio de email:** `cambiarEmail` pide la contraseña actual y deja que Supabase mande el enlace de confirmación; no cambia nada hasta que se confirma. Cuando la sesión ya trae el email nuevo, `usuarioActual()` pone al día `usuarios.email`, el contacto del perfil de docente (solo si era el mismo que el de la cuenta) y la membresía de equipo (`sincronizarEmailDeCuenta`, `src/lib/queries/email-cuenta.ts`). Quien ingresa solo con Google no puede cambiarlo. **Sin probar de punta a punta con un mail real** (hace falta el correo de producción funcionando).
- **Términos:** `usuarios.terminos_aceptados_en` y `terminos_version` guardan cuándo se aceptaron y cuál era la versión (`src/lib/terminos.ts`). **Todos** (profesional, institución y quien llega por una invitación) los aceptan en el **paso 1** del alta, con la casilla del formulario de registro (`registrarse` y `ingresarConGoogle` la exigen para cualquier rol; sin ella no se crea la cuenta): con email la constancia va en `user_metadata`; con Google, en una cookie de una hora; en los dos casos se copia al crear la fila `usuarios` (`asegurarUsuario`). El paso 2 de la institución (`crearInstitucion`) solo vuelve a pedir la casilla si la cuenta no tiene constancia (cuentas anteriores o cookie vencida) y ahí el servidor la exige. **Lo mismo el "¿Qué sos?" del profesional** (`guardarCategoriaDocente`, primer paso con sesión, donde se crea su perfil): pide la casilla si la cuenta no tiene constancia y el servidor la exige antes de crear nada. Es el caso de **quien entra con Google desde "Ingresar" sin tener cuenta** (`ingresarConGoogle(null)` no pide términos ni deja cookie): `/inicio` lo manda a `/registro`, elige "Soy profesional" y cae acá. Se vio en la primera prueba de Google en producción (2026-10-13): la cuenta quedó sin constancia.
- **Nombre y apellido del profesional:** el registro los pide **por separado** (`nombre`, `apellido`; se guardan en `user_metadata` y `datosDeSesion` expone los dos), porque partir un nombre completo por la última palabra falla con apellidos dobles ("Juan Pérez García"); con Google viene el nombre completo y se parte con `partirNombre`. El paso 3 del alta ("Tus datos personales") **no vuelve a pedirlos**: se corrigen en Mi perfil hasta que se verifica el DNI.
- **"Volver" del registro** lleva al inicio (`/`), no al selector `/registro`: quien entró como institución no ve "Soy profesional". El selector queda para "Crear cuenta" del menú y el ingreso. **Crear la cuenta se ve igual que ingresar** (2026-10-16): el paso 1 del alta del profesional y de la institución usa `MarcoAcceso` (foto con la marca a la izquierda, tarjeta blanca a la derecha; cada rol con su foto y su texto de `PORTADA_ONBOARDING`) y el "Volver al inicio" lo pone el marco. **Los pasos siguientes del alta** (2 a 6 del profesional, 2 y 3 de la institución) usan `MarcoOnboarding`, con la misma identidad: comparte con `MarcoAcceso` el panel de la foto (`PanelDeFoto`, que acá queda fijo mientras se desplaza el formulario y en ≤ 860 px pasa arriba) y el formulario va en una tarjeta blanca redondeada con el encabezado (paso + "Guardar y salir"), la barra de progreso y el contenido. **Los botones principales del alta son azules** para los dos roles (antes los del profesional eran coral, `variante="cta"`): el ingreso y el alta se ven igual; el coral queda para los botones de llamada a la acción del sitio. **Al cambiar el texto de `/terminos`, subir `VERSION_TERMINOS` y `TERMINOS_ACTUALIZADOS`** (hoy `2026-10`; no hay un flujo que le pida una nueva aceptación a quien ya aceptó otra versión: solo queda la versión que aceptó). El texto es el documento legal que redactó la titular y vive como datos en `src/lib/terminos-texto.ts` (secciones numeradas, listas, `**negrita**` y `[enlace](/ruta-interna)`), con una prueba que cuida que no falte una sección ni quede una marca suelta: **se carga tal cual, no se reescribe**. Las cuentas anteriores a este registro quedan sin constancia (null).
- **Enlaces de los mails de Auth:** los de **confirmación de registro** y de **recuperación de contraseña** llevan `token_hash` y llegan a `/auth/confirmar` (`src/app/auth/confirmar/page.tsx`), que **solo muestra un botón**: el token se verifica en el servidor (`verifyOtp`) cuando la persona lo toca (acción `confirmarEnlace`, `src/app/actions/auth.ts`), no al abrir la dirección. Así los antivirus y los "vínculos seguros" de Outlook, que abren los enlaces de los mails para revisarlos, no gastan el token antes de que llegue a quien lo recibió. Andan desde cualquier dispositivo, y la sesión queda en el que tocó el botón. Los demás (cambio de email, magic link) siguen con el enlace de Supabase por `/auth/callback` (PKCE), que **solo anda en el mismo navegador** donde se pidió. Las plantillas de `supabase/plantillas-correo/` se pegan a mano en el panel de Supabase: si cambia el enlace de una, hay que volver a pegarla. Detalle en `docs/supabase-auth.md`.
- **Google:** el botón "Continuar con Google" se muestra solo si Supabase informa el proveedor como activado (`googleHabilitado()`, lee `/auth/v1/settings` y guarda 5 minutos): no hay una variable aparte que cambiar.
- **Redirecciones:** todo destino que llega desde el navegador (`?next=`) se valida con `rutaInternaSegura` (`src/lib/acceso.ts`, con pruebas). Una versión anterior dejaba pasar `/..//sitio.com` (quedaba `//sitio.com` al normalizar y mandaba a otro dominio): si se toca, correr `pnpm test`.
- **Contraseñas:** el registro pide repetirla y todos los campos tienen "Ver / Ocultar" (`InputContrasena`).
- **Privacidad:** `/privacidad` describe lo que el sistema hace con los datos (quién ve qué, documentos, proveedores, cookies). Hay que actualizarla, y su fecha (`PRIVACIDAD_ACTUALIZADA`), cuando cambie ese comportamiento. Es un borrador técnico sin revisión legal: faltan, por ejemplo, la identificación del responsable del tratamiento, el registro de la base ante la AAIP y la cláusula de transferencia a servidores en Brasil.

### Correo

Dos canales que no se mezclan: los mails de **Auth** (confirmación, recuperación, cambio de email, avisos de seguridad) los manda Supabase con las plantillas de `supabase/plantillas-correo/`; **todo lo demás** lo manda nuestro código por la API de Resend (sin SDK). Guía completa: `docs/correo.md`; qué mail existe y a quién llega: `docs/inventario-de-mails.md` (los IDs M06, M24… son los del código).

- **Cola ("outbox"):** `cola_correos` (creada a mano con RLS: Drizzle no lo conoce y un `db:push` llegó a apagárselo, así que **después de cualquier `db:push` correr `db:rls` y confirmar que ninguna tabla pública quedó sin RLS**). Las acciones llaman a `encolarParaUsuarios` / `encolarParaEquipo` / `encolarCorreo` (`src/lib/correo/cola.ts`), casi siempre a través de una función de `src/lib/correo/eventos.ts`, **dentro de su transacción**: si se deshace, el mail no existe. `encolar…` deja pedido el despacho con `after()` (corre con la transacción ya confirmada), así que las acciones no llaman a nada más. Los reintentos y los mails vencidos (48 h) los resuelve el cron `/api/cron/correos` (13:00 UTC), que también anota los recordatorios M51/M52 y purga el historial a los 90 días.
- **Apagado sin clave:** sin `RESEND_API_KEY` (o con `CORREO_MODO=apagado`) no se anota ni se manda nada; `CORREO_MODO=consola` solo imprime, para probar. `/api/salud` muestra el modo en `correo`. Variables y pasos para encenderlo: `docs/correo.md`.
- **Plantillas** (`src/lib/correo/plantillas.ts`, código puro con pruebas): el texto de las personas se escapa siempre y va como `Parte` o `cita`, nunca pegado en el HTML. Las rutas de los enlaces son internas y se arman contra `NEXT_PUBLIC_SITE_URL`; una ruta externa hace fallar ese mail. Un mail nuevo = su ID en `DatosDe` y `PLANTILLAS`, un ejemplo en `plantillas.test.ts`, una función en `eventos.ts` con su **clave de no-repetición**, y el inventario y `/privacidad` al día.
- **Cerrar una búsqueda avisa en la campanita, sin mail** (a propósito): `avisarCierreDeBusqueda` (`src/lib/queries/avisos.ts`; texto en `textoDeCierreDeBusqueda`, `src/lib/postulaciones.ts`) lo llaman `cerrarBusqueda` y `contratarPostulacion` con "cerrar". Avisa a quienes estaban en la búsqueda con cuenta y sin suspender, menos al contratado, y no repite en el día.
- **Quién decide si sale:** el grupo `contratacion` (invitaciones, urgentes, preselección, entrevistas, ofertas, postulantes nuevos) respeta `usuarios.avisos_por_correo` (interruptor en Mi cuenta y enlace de baja firmado, `/avisos/baja` + `/api/avisos/baja` para el POST de un clic); cuenta, verificación, facturación e internos no se pueden apagar. Hay topes (M21: 3 por día por persona, M06, M60, M61) y los **contactos privados de las instituciones no reciben nunca ningún mail**. **Archivar a un postulante (etapa interna `descartado`) es silencioso a propósito: no se le avisa ni en la campanita ni por mail** (no existe un M28); se entera, si la búsqueda se cierra, por el aviso de cierre. Mientras tanto el docente ve su postulación archivada como "Postulación enviada" (`estadoParaDocente`, `src/lib/postulaciones.ts`), y al cerrarse la búsqueda como "Búsqueda cerrada".
- **La base local es la de producción y el envío de producción está encendido:** una fila pendiente de `cola_correos` que quede de una prueba la puede despachar producción de verdad (cualquier acción o el cron). Probar solo con `CORREO_MODO=consola` y direcciones propias, y borrar las filas al terminar.
- Facturación y plan salen desde `facturacion@` a dueño y administradores (`destinatariosDeFacturacion`); Contacto, documentación, bajas y pedidos de plan van al equipo (`CORREO_EQUIPO` o las cuentas admin, con "responder a" la persona en Contacto).
